# 定向文献调研:GRPO 从强 SFT 起点坍缩(2026-08-13,回应 T2.1 负结果)

> 调研方式:WebSearch 多轮交叉(WebFetch 被环境拦截,数字置信度已标注)。与 docs/research_track_20260813.md 互为姊妹篇。

## 核心结论

1. **T2.1 回吐机理 = 文献公认坍缩签名**:稀疏奖励组内 std 趋零 → 优势≈0、梯度退化;叠加长度归一化偏差(Dr. GRPO)与对称裁剪压制低概率 token → 熵单调坍缩。-11.4pp + 执行率下降与"训练后期行为被洗掉"一致。
2. **稠密化是对症的、文本SQL-RL 主流共识**(SQL-R1 四层递进 / Reasoning-SQL 部分奖励套件 / EDGE-GRPO 熵驱动优势)。我们的 0.5+0.5×atomic 与这些同构,建议再加软格式分并保持"结果正确"最高优先级。
3. **强 SFT 起点防遗忘 = 约束而非放开**:保留 KL(β=0.02 合理,2502.18548:β 是"锁回 SFT 的旋钮",不能设 0);lr 上限 ~2e-6(SQL-R1 社区报告 3e-7 量级);短程训练(多数工作 5-20 epoch 刻意短程);**10-15% SFT 数据混入 RL 批次是已证实防遗忘手段**(CHORD/2510.04454)。
4. **反例数据点**:Arctic-Text2SQL-R1(2505.20315)用简单二值执行奖励从强 Instruct 起点成功(Spider 88.8)——坍缩主因更可能是"稀疏三元+优化器设置"而非"必须稠密"。
5. **3B 特有风险**:~200 步后语言混合/长度失控/test 回吐(2503.16219:500 步时无法生成纯英文,AIME25 低于基座)。对策:监控 std 与熵、短程、验证集早停、RePO 经验池(≤3B 增益最大:+18.4pp@1.5B)。

## T2.3 备选配方(若 T2.2 仍不理想)

现有稠密奖励之上叠加:DAPO 加固(clip_ratio_high=0.28、过滤组内奖励全同样本、loss_agg=token-mean;注:TRL 0.15.2 无这些参数,需 TRL 0.16.1+全部依赖已装+judges 补丁,升级路径已打通待验证);保持 β=0.02/lr 2e-6/40 步;RL 批次混 10-15% 原 SFT 样本;奖励加软格式分;每步记录组奖励 std 与策略熵,熵跌至初期一半即早停;仍不稳 → lr 3e-7 + RePO 经验池。
